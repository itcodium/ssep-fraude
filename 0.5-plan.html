00
Cómo leer este plan
Tres supuestos · tres advertencias

Este documento asume tres cosas:

  • Un perfil base concreto: desarrollador senior con experiencia en Python, ML básico y backend. Ajusto tiempos para otros perfiles al final.
  • Un dominio ya elegido. Si aún no sabes si aplicas la base a motores, fraude o médico, esta estimación no aplica.
  • Dedicación a tiempo parcial realista. Los tiempos incluyen interrupciones normales, no son días de 12 horas sin fricción.
⚠ Advertencia sobre los bloqueadores El código es la parte rápida. Los bloqueadores reales son: conseguir documentos reales, generar datasets etiquetados, y producir queries de prueba. Estas tareas dependen de terceros y suelen tardar más que el código. El plan las marca explícitamente.

02
Fase A — Diseño de la base
3 tareas · sin código · obligatorio

Es la fase que parece trivial y no lo es. Todo lo demás depende de las decisiones tomadas aquí. Si esta fase se hace mal, el código se reescribe después.

FASE A Diseño de la base 0.5 día
A1
Elegir el dominio de la IMR. Un caso concreto: motores, fraude, médico, u otro. Debe cumplir las 10 condiciones del Doc 0 §1.
2-4 h
A2
Definir los 3 contratos. Escribir los JSON exactos de evento, predicción y explicación para ese dominio. Los tres campos base se mantienen; los específicos se añaden.
3-4 h
A3
Confirmar las 3 reglas. Verificar que en el dominio elegido: cada capa tiene una sola responsabilidad, la capa 3 no modifica la predicción, y la abstención es posible.
1 h
⚠ Bloqueador real Elegir mal el dominio es el error más caro. Si la capa 3 (explicación) no aporta valor — porque el problema no necesita explicación, o porque no hay documentación experta — el patrón es sobredimensionado. No continúes a Fase B hasta estar seguro.
03
Fase B — Implementación Mínima de Referencia
6 tareas · ~150 líneas · obligatorio

La IMR es la implementación más pequeña posible de la base. 3 archivos Python + 3 carpetas. Sin Kafka, sin Qdrant, sin LLM. Corre en cualquier portátil con python main.py.

FASE B IMR — Implementación Mínima de Referencia 2 días
B1
Estructura del proyecto. Crear ssep_referencia_minima/ con subcarpetas docs/ y datos/.
30 min
B2
Capa 1 — Ingesta. capa1_ingestion.py: leer señal, extraer features, producir evento con el contrato exacto.
2-3 h
B3
Capa 2 — Modelo. capa2_model.py: clasificador trivial (reglas) o sklearn muy pequeño.
3-4 h
B4
Capa 3 — Explicación. capa3_explanation.py: retrieval simple, síntesis con plantilla, abstención si no hay fuentes. Es la capa más compleja.
4-6 h
B5
Orquestador. main.py: conectar las 3 capas, ejecutar con 3 casos de prueba.
1-2 h
B6
Datos y documentos. 3 documentos en docs/ (texto plano), 3 señales en datos/ (o generadas).
2-3 h
Nota sobre la capa 3 Es donde más se aprende y donde más tiempo se invierte. La abstención explícita (regla 3) es un requisito, no una opción. Si la implementación no puede abstenerse, está mal.
04
Fase C — Validación
3 tareas · criterio de salida

La IMR sirve de algo solo si funciona. Esta fase verifica que el flujo end-to-end produce resultados coherentes y que las 3 reglas se cumplen en código, no solo en papel.

FASE C Validación de la IMR 0.5 día
C1
Ejecutar con los 3 casos. Verificar que el flujo end-to-end produce output coherente en cada uno.
1-2 h
C2
Verificar la regla 3 (abstención). El sistema debe decir "no tengo información" cuando no hay docs. Probar con un caso sin documentación.
1 h
C3
Verificar la regla 2 (no modifica). La capa 3 no altera label ni confidence. Comparar predicción de entrada con el label de salida.
1 h
✓ Criterio de salida de la Fase C Puedes mostrar el output a alguien ajeno al proyecto y esa persona entiende qué ha pasado sin que se lo expliques. Si no, la base no está lista para escalar.
05
Peldaños 1-5
Extensiones · opcionales · secuenciales

Cada peldaño sustituye una pieza de la IMR por su versión real. La arquitectura no cambia — solo el contenido de cada capa. Cada peldaño se sube solo cuando el anterior está validado.

PELDAÑO 1 Modelo real 3-5 días
P1.1
Dataset mínimo. 100-500 ejemplos etiquetados del dominio. Es el bloqueador más lento del peldaño.
1-3 d
P1.2
Entrenamiento. Modelo pequeño: sklearn, XGBoost, o PyTorch según dominio.
1-2 d
P1.3
Serving. FastAPI o función que carga el modelo y sirve predicciones.
0.5 d
P1.4
Integrar en IMR. Sustituir la función classify() por la llamada al modelo real. Sin tocar las otras dos capas.
0.5 d
PELDAÑO 2 RAG real 5-7 días
P2.1
Preparar documentos. 20-50 documentos reales en texto plano. Depende de terceros. Bloqueador.
1-3 d
P2.2
Chunking. Dividir en fragmentos con sentido semántico, no por caracteres fijos.
1 d
P2.3
Embeddings + vector store. pgvector o Chroma local. BGE o similar para embeddings.
1 d
P2.4
Búsqueda + reranking. Top-K + cross-encoder pequeño (ms-marco-MiniLM) con threshold 0.5.
1-2 d
P2.5
Integrar en IMR. Sustituir la búsqueda por keyword. Sin tocar las otras dos capas.
0.5-1 d
PELDAÑO 3 LLM real 3-5 días
P3.1
Levantar LLM local o conectar API. Ollama con Llama 3.2 3B, o llamada a Claude/GPT-4o-mini.
1 d
P3.2
Prompt grounded. Plantilla que fuerza el uso exclusivo de los chunks como fuente. Aquí se gana o se pierde la calidad.
1-2 d
P3.3
Integrar en IMR. Sustituir la síntesis por la llamada al LLM. Sin tocar las otras dos capas.
1-2 d
PELDAÑO 4 Observabilidad 3-5 días · paralelizable
P4.1
Desplegar Langfuse. Docker Compose local o K8s. Self-hosted obligatorio si hay datos de cliente.
1 d
P4.2
Instrumentar con @observe(). Decorar la función principal. Trazas automáticas.
0.5 d
P4.3
Validar trazas. Ver que cada request tiene su trace completo con input, output, coste, latencia.
1-2 d
PELDAÑO 5 Evaluación 5-7 días
P5.1
Preparar 20-100 queries de prueba. Con respuesta esperada. Trabajo manual. Bloqueador.
2-3 d
P5.2
Configurar RAGAS. Pipeline de evaluación con las 4 métricas: faithfulness, relevancy, precision, recall.
1 d
P5.3
Establecer baseline. Ejecutar evaluación, documentar scores, definir gate de calidad.
1-2 d
⚠ Regla de crecimiento Cada peldaño se sube solo cuando el anterior está validado. El error más común es saltar del Peldaño 0 al 5 y terminar con un sistema complejo que no funciona en el 0.

07
Camino crítico
Los 4 bloqueadores reales

El camino crítico de este plan no es el código. Es todo lo que depende de terceros o de trabajo manual no automatizable. Estos son los 4 bloqueadores que hay que resolver para que los tiempos se cumplan.

Camino crítico · bloqueadores
1Elegir dominio correcto
Fase A · 2-4 horas. Si el dominio elegido no cumple las 10 condiciones del Doc 0, todo lo demás es trabajo perdido. Coste de equivocarse: semanas.
2Conseguir documentos reales
Peldaño 2 · 1-3 días. Depende de terceros: fabricantes, legal, clientes. Sin documentos reales, el RAG solo tiene sintéticos y no vale.
3Generar dataset etiquetado
Peldaño 1 · 1-3 días. Trabajo manual o de expertos del dominio. No se puede automatizar sin perder calidad.
4Producir queries de prueba
Peldaño 5 · 2-3 días. Sin queries de prueba, no hay evaluación. Sin evaluación, no sabes si el sistema mejora.
⚠ Implicación El código de la base se hace en 3 días. Los bloqueadores añaden 1-2 semanas de espera o trabajo manual. Si dependes de terceros para documentos o etiquetas, empieza a pedirlos en Fase A, no cuando los necesites.

09
Reglas de decisión
Cuándo subir al siguiente peldaño · cuándo parar

Antes de subir al siguiente peldaño, hazte estas 4 preguntas. Si alguna respuesta es "no" o "no sé", no subas.

1
¿El peldaño actual me da valor?
Si el peldaño actual no aporta valor en tu dominio, el siguiente probablemente tampoco. Detente y revisa si el dominio elegido es el correcto.
2
¿El bloqueador del siguiente peldaño está resuelto?
Ejemplo: no subas a Peldaño 2 si no tienes documentos. No subas a Peldaño 1 si no tienes dataset. Los bloqueadores son humanos, no técnicos.
3
¿Tengo claro qué mejora concreta espero del siguiente peldaño?
"Mejorar la calidad" no es una respuesta. "Reducir alucinaciones un 30%" o "detectar drift antes de 24h" sí lo es.
4
¿Puedo parar aquí y el sistema sigue siendo útil?
Si no, hay dependencia estructural entre peldaños que debería estar resuelta por la arquitectura. Revisa los contratos.
Cada peldaño es autónomo. Si el proyecto se detiene en el Peldaño 2, ya tienes un sistema con modelo real y RAG real. Si se detiene en el Peldaño 5, tienes un sistema medible. Ningún peldaño depende de que el siguiente exista.
10
Qué cambia según perfil
Ajustes concretos para cada caso

Senior con ML

  • Sigue el orden indicado. Los tiempos son realistas.
  • Puede paralelizar Peldaños 1 y 2 desde el principio (si tiene dataset y documentos).
  • No necesita apoyo externo para el código.

Mid-level con apoyo

  • Suma un 50% al tiempo de cada peldaño.
  • Necesita revisión de código externa antes de escalar del Peldaño 3 al 4.
  • Puede hacer Fases A, B y C sin ayuda.

Sin experiencia ML

  • Empieza por Fase B sin modelo real (clasificador trivial).
  • Sube a Peldaño 1 solo cuando entiendas los contratos.
  • No intentes Peldaño 3 sin haber hecho Peldaño 2 completo.
  • Considera apoyo externo para el fine-tuning del Peldaño 4.

Equipo de 2-3 personas

  • Paralelizar Peldaños 1, 2 y 4. Peldaño 3 en serie con el 2.
  • Los tiempos no bajan linealmente. La coordinación tiene coste.
  • Designar a alguien como responsable de contratos e interfaces.
  • Reunión semanal de sincronización para no desviar la arquitectura.
✓ Cómo usar este plan Este plan no es un contrato. Es una referencia para estimar. Cuando el primer dominio esté implementado hasta Peldaño 5, tendrás datos reales sobre cuánto tarda tu equipo en cada peldaño. A partir de ahí, tus estimaciones serán mejores que las de este documento.
El código es la parte rápida. Lo lento son las decisiones correctas (Fase A), los datos reales (Peldaños 1 y 2), y la evaluación honesta (Peldaño 5). Si esos tres puntos están resueltos, el resto es mecánico.
