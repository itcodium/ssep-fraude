00
Cómo leer este documento
Tres reglas · tres atajos

Este documento no es una receta. Es un catálogo de opciones para materializar cada una de las cinco capas del patrón SSEP. Cada capa tiene múltiples herramientas viables y ninguna es universalmente correcta — la elección depende de cuatro variables: volumen, latencia objetivo, equipo disponible y presupuesto operacional.

1
No busques "la mejor" herramienta
Busca la que encaja con tu volumen, equipo y restricciones. Kafka es la respuesta correcta para >10k msg/s y la respuesta incorrecta para <1k msg/s operado por una persona.
2
Cada opción tiene coste operacional explícito
No solo coste económico. También coste de aprendizaje, de mantenimiento, de contratación. Un Kafka bien operado cuesta más que una cola en Redis aunque el hardware sea el mismo.
3
Los stacks (§07) son el atajo
Si no quieres leer el catálogo completo, ve directo a §07 y elige el stack que más se parezca a tu situación. Después vuelve a las capas específicas que necesites ajustar.

1.1 Transporte de eventos

La capa de transporte mueve eventos del origen al sistema de cómputo. La decisión depende fundamentalmente del volumen y de si necesitas replay.

Opción
Cuándo elegirla / evitarla
Coste operacional
Kafka
Elegir: >10k msg/s, replay, múltiples consumers independientes, retención larga. Evitar: <1k msg/s o equipo sin experiencia.
Alto — brokers, tuning, ZK/KRaft, on-call
Redpanda
Elegir: igual que Kafka pero quieres menos operación (binario único, sin ZK). Evitar: necesitas ecosistema máximo de conectores.
Medio — un solo binario, API compatible Kafka
Pulsar
Elegir: multi-tenant, geo-replicación nativa, colas + streaming unificados. Evitar: equipo pequeño.
Alto — muchos componentes (broker, bookkeeper, ZK)
NATS JetStream
Elegir: latencia ultra-baja, operación simple, <100k msg/s. Evitar: retención larga o replay masivo.
Bajo — binario único, sin dependencias
MQTT (Mosquitto/EMQX)
Elegir: dispositivos con recursos limitados, redes inestables, protocolo IoT estándar. Evitar: procesamiento stream nativo.
Bajo-Medio — simple, pero necesita bridge a Kafka
RabbitMQ
Elegir: colas tradicionales, routing complejo, <5k msg/s. Evitar: replay o consumer groups múltiples.
Medio — Erlang, plugins, HA configurable
Redis Streams
Elegir: ya tienes Redis, volumen moderado, simplicidad. Evitar: retención larga, múltiples consumers independientes.
Bajo — ya está en el stack
Cloud managed
Kinesis (AWS), Pub/Sub (GCP), Event Hubs (Azure). Elegir: estás en cloud y quieres olvidarte de la operación. Evitar: on-prem, coste por mensaje prohibitivo.
Managed — pagas por uso
Regla práctica Si los dispositivos son IoT con recursos limitados → MQTT en el borde, Kafka en el centro. MQTT no reemplaza a Kafka, lo alimenta. El bridge (EMQX + kafka-connect o similar) es la frontera.

2.4 Calibración e incertidumbre

No hay debate — son librerías específicas:

Necesidad
Librería
Cuándo
Calibración de probabilidades
sklearn.calibration (Platt, isotonic), netcal
Siempre que un threshold numérico importe. Un 0.9 sin calibrar no significa 90% real.

3.3 Retrieval y reranking

Técnica
Cuándo
Coste operacional
Búsqueda densa
Vector store por defecto. Suficiente para queries semánticas simples.
Bajo
Búsqueda híbrida (BM25 + densa)
Cuando hay términos técnicos exactos que la densa pierde. Qdrant/Weaviate/Milvus lo soportan nativo.

5.5 Feedback loop

No hay herramienta estándar. Es decisión de producto:

  • UI de revisión — el operador marca "correcto / incorrecto / corregir a X".
  • Almacenamiento — vuelve al data lake versionado con DVC/LakeFS.
  • Priorización — muestrear casos de alta incertidumbre para revisión primero.
  • Trigger de reentrenamiento — cuando se acumulan N etiquetas nuevas (no cada semana).

6.3 Auditing

Toda la instrumentación de seguridad va a tres destinos correlacionados por trace_id:

  • Langfuse — span de seguridad en cada traza, correlacionado con la request.
  • ClickHouse — tabla security_events con tipo, severidad, usuario, patrón matchado.
  • Loki — búsqueda de texto sobre los patrones de ataque (forense).

08
Anti-selecciones
Qué NO usar · y por qué

Tan importante como saber qué elegir es saber qué evitar. Estas son combinaciones que parecen razonables pero que producen deuda técnica, coste operacional injustificado o fallos silenciosos.

Anti-selección
Por qué evitarla
Spark para <1000 msg/s
Overhead operacional desproporcionado. Un consumer Python es suficiente.
Kubernetes para MVP de 1 persona
Complejidad que no pagas. Docker Compose es suficiente hasta que no lo sea.
Pinecone si puedes usar pgvector
Managed innecesario si <1M vectores. pgvector ya está en tu Postgres.
LLM-as-judge en path síncrono
Latencia ×3, coste ×3, sin ganancia real. Muévelo a background con sampling.
Triton si no compartes GPU
FastAPI + ONNX Runtime cubre el caso. Triton añade complejidad de configuración por modelo.
MLflow si solo tienes 1 modelo
DVC + git tags sobra. MLflow se justifica cuando hay >3 modelos o múltiples personas.
LangChain si controlas 5 llamadas
La abstracción cuesta más de lo que aporta. Llamadas directas son más claras.
Evidently si no vas a mirar dashboards
Instrumentación sin uso es deuda. Si nadie va a actuar sobre el drift, no lo midas.
Custom vector store
Nunca. Usa uno existente. Ya hay cinco que cubren todos los casos.
LangSmith con datos de cliente
Brecha SOC2/ISO27001. El trace completo (prompt + completion) va a servidores de terceros.
Fine-tuning antes de medir RAG
Optimizas sin baseline. No sabrás si mejoró. Primero RAGAS, después Unsloth.
ClickHouse como único sistema de observabilidad
No sustituye a Prometheus para alertas en tiempo real. Complementa, no reemplaza.
LangGraph para 2 pasos lineales
El grafo es overhead. Si no hay ciclos ni human gate, una función secuencial basta.
LLM-as-judge en cada request
Latencia ×3, coste ×3. Muestreo (20%) da señal suficiente.
Guardrails propios con regex
NeMo existe y es mantenido. Escribir tus propios guardrails es reinventar mal algo que ya está resuelto.
09
Criterios de decisión
Cómo elegir cuando dudes entre dos opciones

Cuando dos opciones parecen igualmente viables, decide por este orden. Cada paso elimina parte de las opciones.

1
Volumen
¿Cuántos eventos por segundo? <100/s → consumer directo. 1k-10k/s → Kafka. >10k/s → Kafka + Flink. Este criterio elimina la mitad de las opciones.
2
Latencia objetivo
¿Milisegundos o segundos? <100ms → Flink, no Spark. <5s end-to-end → permite LLM en el path. Si necesitas <50ms, el LLM no puede estar en el path crítico.
3
Equipo disponible
¿Quién va a operar esto en 2 años? Si no tienes equipo Kafka, no uses Kafka. La herramienta más sofisticada operada por nadie es peor que la herramienta simple operada por alguien.
4
Presupuesto
No solo infra: también tiempo de ingeniería. Un Kafka bien operado consume 0.5 FTE. Un ClickHouse, otros 0.3. Súmalos antes de comprometerte.
5
Madurez del dominio
MVP o producto estable. En MVP → stack minimal. En producto → stack completo. No construyas para el producto que no tienes todavía.
6
Restricciones externas
On-prem obligatorio, cumplimiento, latencia geográfica. Estas restricciones eliminan opciones antes de empezar: LangSmith SaaS no es viable si SOC2 requiere soberanía.
La herramienta correcta no es la más sofisticada. Es la que tu equipo puede operar, tu presupuesto puede sostener, y tu volumen justifica. Todo lo demás es sobre-ingeniería disfrazada de buenas prácticas.
