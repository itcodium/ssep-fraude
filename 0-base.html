00
Propósito
Por qué existe este documento

El Doc 1 describe el patrón SSEP completo: 5 capas, 6 herramientas transversales, sistema industrial. Ese es el destino. Este documento es el punto de partida.

La base tiene un solo objetivo: demostrar que el flujo señal → clasificación → explicación tiene sentido en tu dominio. Si no lo tiene, ninguna cantidad de Kafka, Qdrant o LangGraph lo va a arreglar.

Regla del documento Si algo de este documento no se puede implementar con 3 funciones Python y 3 carpetas, no es base — es extensión. Las extensiones viven en los Docs 0.6, 0.7, 1, 2 y 3.
01
Contexto
Cuándo aplica · cuándo NO aplica

El patrón SSEP aplica cuando concurren todas estas condiciones. No es un patrón universal — es específico para un tipo de problema que aparece repetidamente en dominios industriales, médicos, financieros y agronómicos.

Señales de que aplica

  1. Existe una señal física continua (audio, vibración, temperatura, imagen, telemetría, transacciones) generada por múltiples fuentes distribuidas.
  2. Un modelo ML puede clasificar el estado de esas fuentes con precisión útil, pero no puede explicar por qué.
  3. Existe conocimiento experto documentado (manuales, guías, normativa, casos previos) que un humano consultaría para decidir qué hacer.
  4. El coste de un falso negativo es alto (fallo no detectado = pérdida económica, riesgo físico, daño reputacional).
  5. El coste de un falso positivo también importa (fatiga de alertas, intervenciones innecesarias).
  6. Las condiciones de producción difieren inevitablemente de las de entrenamiento.
  7. Un operador humano toma la decisión final, asistido por el sistema, no reemplazado por él.
  8. Existe un LLM base de propósito general que puede especializarse con datos del dominio.
  9. El sistema opera en un entorno regulado (SOC2, ISO 27001, HIPAA) donde la soberanía de datos es un requisito.
  10. Los flujos de decisión pueden ser multi-paso y requieren estado persistente entre pasos.

Señales de que NO aplica

  • La señal es puntual, no continua.
  • El modelo puede actuar autónomamente sin supervisión humana.
  • No existe documentación experta que consultar — el RAG no aportaría nada.
  • El coste de un error es despreciable.
  • Las condiciones de producción son idénticas a las de entrenamiento.
  • No hay requisitos de cumplimiento ni auditoría.
  • No hay volumen suficiente para justificar el coste operacional completo.
⚠ Decisión crítica Si faltan las condiciones 4 y 5 (coste alto de falso negativo y falso positivo), el patrón es sobredimensionado. Un sistema de clasificación simple con revisión manual es suficiente. SSEP se justifica por la asimetría de costes y la necesidad de explicación grounded.

Lo que la base NO tiene: Kafka, Qdrant, LangGraph, Langfuse, Evidently, ClickHouse, guardrails, drift detection, agentes, fine-tuning. Todo eso son extensiones que se justifican después de que la base funcione.

✓ La base es un contrato, no una infraestructura La base define qué pasa entre capas, no cómo se implementa cada capa. Eso la hace reutilizable: cada dominio rellena las 3 capas con su contenido, pero los contratos se mantienen.
03
Contratos entre capas
Lo único que la base define con precisión

Los contratos son la parte más importante de la base. Definen la forma exacta de los datos que cada capa entrega a la siguiente. Si cambias un contrato, cambias la arquitectura.

Capa 1 → Capa 2evento
{ source_id: string, # identidad del origen timestamp: ISO8601, # cuándo se capturó features: object, # representación compacta de la señal metadata: object # contexto adicional (opcional) }
Capa 2 → Capa 3predicción
{ label: string, # clase asignada confidence: float, # 0.0 – 1.0, calibrada uncertainty: float, # 0.0 – 1.0, epistémica model_version: string, # trazabilidad source_id: string # heredado de la capa 1 }
Capa 3 → Consumidorexplicación
{ explanation: string, # texto grounded en fuentes sources: array, # documentos citados grounding_score: float, # 0.0 – 1.0, adherencia a fuentes label: string # etiqueta original, sin modificar }

Por qué estos contratos y no otros: la capa 3 necesita confidence y uncertainty porque son cosas distintas — una predicción puede ser confiada pero epistémicamente incierta. La capa 3 devuelve grounding_score porque el consumidor necesita saber si la explicación está respaldada. Y devuelve el label sin modificarlo porque la capa 3 nunca decide.

04
Reglas invariantes
3 reglas · se cumplen en cualquier dominio

Estas tres reglas son lo que distingue esta arquitectura de cualquier pipeline ML convencional. Si se rompen, la base deja de ser reutilizable.

1
Cada capa tiene una sola responsabilidad
Ingesta no clasifica. Modelo no explica. Explicación no decide. Cualquier intento de mezclar responsabilidades convierte la arquitectura en un monolito disfrazado de pipeline.
2
La capa de explicación nunca modifica la predicción
Puede enriquecerla con contexto, pero no puede cambiar la etiqueta ni la confianza. Si el sistema empieza a "corregir" al modelo desde la capa 3, se pierde la trazabilidad y el modelo deja de ser auditable.
3
Si no hay fuentes, la capa 3 se abstiene explícitamente
El sistema debe poder decir "no tengo información suficiente" en lugar de generar. Esta es la diferencia entre un sistema útil y un generador de alucinaciones. La abstención es una respuesta válida, no un fallo.
Tres reglas. Si se cumplen, el sistema es auditable, compone, y crece sin rehacerse. Si se rompen, cualquier complejidad que se añada encima amplifica el problema original.
05
Cómo se extiende
De la base al sistema completo · 9 peldaños

La base no crece "hacia arriba" (más capas apiladas). Crece "hacia los lados" (más componentes dentro de cada capa existente). Esto es lo que mantiene la arquitectura reutilizable: las capas son fijas, los componentes cambian.

Aplicabilidad
La misma base · 3 dominios distintos

Lo que hace reutilizable a la base es que las 3 capas no cambian entre dominios. Lo único que cambia es qué se mete dentro de cada capa. Esta tabla lo muestra:

Los tres dominios comparten los mismos contratos y las mismas reglas. Solo cambia el contenido de cada capa. Esa es la prueba de que la arquitectura es reutilizable.

07
Siguiente paso
De la arquitectura al código

Esta arquitectura no sirve de nada hasta que corre. El siguiente paso es implementarla en su forma más pequeña posible: la Implementación Mínima de Referencia (IMR).

✓ Qué es la IMR La IMR es la implementación en código de esta base. 3 archivos Python, 3 carpetas, ~150 líneas. Corre en cualquier portátil sin infraestructura. Demuestra el flujo end-to-end con datos sintéticos y documentos de ejemplo.

Una vez la IMR funciona en tu dominio, tienes tres caminos:

  • Si aporta valor → subir al Peldaño 1 y empezar la escalera de extensiones.
  • Si no aporta valor → el problema no necesita esta arquitectura. Detente aquí, has ahorrado meses.
  • Si aporta valor parcial → ajusta la base (contratos, reglas) antes de escalar. La base está pensada para adaptarse a dominios.
La base arquitectónica es un marco, no un sistema. Su trabajo es decirte rápido si el patrón SSEP aplica a tu problema. El resto de documentos solo tienen sentido después de que esta base te haya dado un "sí".
