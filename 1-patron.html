Streaming Sensor-to-Explanation
Pipeline with Continuous
Drift Governance. Alias SSEP · Pipeline Sensor→Explicación · "Escuchar, entender, explicar, vigilar"

Un patrón para construir sistemas que ingieren señales físicas continuas, las clasifican con un modelo ML, generan explicaciones grounded en documentación experta, deciden con asistencia humana, y se auto-monitorean para detectar cuándo dejan de funcionar.

01
Contexto
Cuándo aplica · cuándo NO aplica

El patrón SSEP aplica cuando concurren todas estas condiciones. No es un patrón universal — es un patrón específico para un tipo de problema que aparece repetidamente en dominios industriales, médicos, financieros y agronómicos.

Señales de que aplica

  1. Existe una señal física continua (audio, vibración, temperatura, imagen, telemetría, transacciones) generada por múltiples fuentes distribuidas.
  2. Un modelo ML puede clasificar el estado de esas fuentes con precisión útil, pero no puede explicar por qué.
  3. Existe conocimiento experto documentado (manuales, guías, normativa, casos previos) que un humano consultaría para decidir qué hacer.
  4. El coste de un falso negativo es alto (fallo no detectado = pérdida económica, riesgo físico, daño reputacional).
  5. El coste de un falso positivo también importa (fatiga de alertas, intervenciones innecesarias).
  6. Las condiciones de producción difieren inevitablemente de las de entrenamiento.
  7. Un operador humano toma la decisión final, asistido por el sistema, no reemplazado por él.
  8. Existe un LLM base de propósito general que puede especializarse con datos del dominio para reducir coste, latencia o tasa de alucinación.
  9. El sistema opera en un entorno regulado (SOC2, ISO 27001, HIPAA) donde la soberanía de datos es un requisito, no una preferencia.
  10. Los flujos de decisión pueden ser multi-paso (clasificar → diagnosticar → decidir urgencia → generar orden de trabajo) y requieren estado persistente entre pasos.

Señales de que NO aplica

  • La señal es puntual, no continua (ej: un formulario que se envía una vez).
  • El modelo puede actuar autónomamente sin supervisión humana.
  • No existe documentación experta que consultar — el RAG no aportaría nada.
  • El coste de un error es despreciable.
  • Las condiciones de producción son idénticas a las de entrenamiento y se espera que lo sigan siendo.
  • No hay requisitos de cumplimiento ni auditoría — la observabilidad SaaS es admisible.
  • No hay volumen suficiente para justificar el coste operacional del stack completo.
⚠ Decisión crítica Si faltan las condiciones 4 y 5 (coste alto de falso negativo y falso positivo), el patrón es sobredimensionado. Un sistema de clasificación simple con revisión manual es suficiente. SSEP se justifica por la asimetría de costes y la necesidad de explicación grounded.
02
Problema
Cinco fuerzas en tensión

Los sistemas de monitoreo automático fracasan sistemáticamente en producción por cinco fuerzas simultáneas. Cada una es resoluble por separado. El problema es resolverlas todas sin que ninguna consuma la complejidad total del sistema.

01
La brecha semántica
El modelo produce un número (label=3, confidence=0.87). El operador necesita una decisión (¿paro la máquina? ¿espero? ¿a quién llamo?). Entre ambos hay un salto que ningún clasificador resuelve por sí solo.
02
La brecha de distribución
El modelo se entrenó con datos de laboratorio o históricos. En producción la señal cambia: sensores envejecen, condiciones ambientales varían, aparecen modos de fallo no vistos. El modelo falla despacio y en silencio.
03
La brecha de confianza
Un operador que recibe 200 alertas al día y 30 son falsas deja de mirarlas. Un sistema que no comunica su propia incertidumbre se convierte en ruido de fondo.
04
La brecha de feedback
Las correcciones que el operador hace en el campo (esta alerta era falsa, esta era real pero clasificada mal) se pierden si no hay un mecanismo explícito para capturarlas y devolverlas al ciclo de entrenamiento.
05
La brecha de soberanía y control
El LLM que genera las explicaciones suele ser un SaaS. En entornos regulados, enviar el prompt y el completion completos a un tercero es una brecha de cumplimiento. La especialización del modelo y el auto-alojamiento de la observabilidad no son optimizaciones — son requisitos de admisibilidad.
03
Solución
Cinco capas apiladas · una transversal de seguridad

Una arquitectura de cinco capas apiladas verticalmente, con una capa transversal de seguridad y una de observabilidad. Cada capa resuelve una brecha específica del problema.

Cinco reglas estructurales

  1. Las capas 1→2→3 forman el path síncrono (la respuesta al operador). Las capas 4 y 5 el path de gobierno (meta-información sobre el sistema). Nunca se mezclan en el mismo plano temporal.
  2. La capa 3 nunca decide. Solo explica lo que la capa 2 predijo. Mezclar generación con decisión es el anti-patrón más común de este diseño.
  3. La capa 5 no bloquea las capas 1-2-3. Si el sistema de drift cae, la predicción sigue saliendo. El gobierno es observacional, no transaccional.
  4. La seguridad es transversal: input validation antes de la capa 3, output validation después. Ninguna capa decide por sí sola si un input es malicioso.
  5. La observabilidad es transversal: cada capa emite trazas al mismo sistema con el mismo trace_id propagado desde el sensor físico.
04
Componentes
Rol y responsabilidades de cada capa
CAPA 01 Ingestion Síncrono

Rol: capturar la señal física en su origen, reducirla a un formato transportable, moverla al sistema de cómputo.

Responsabilidades

  • Captura — leer la señal del sensor (audio, vibración, imagen, lectura).
  • Pre-procesado en origen — transformar la señal cruda en features o representaciones compactas antes de transmitirla.
  • Transporte — mover los eventos de forma fiable, ordenada por fuente, con capacidad de replay.
  • Control de flujo — evitar que un pico de eventos tumbe el sistema aguas abajo.
  • Tolerancia a fallos de transporte — mensajes malformados no deben bloquear el pipeline.
Lo que esta capa NO hace: clasificar · decidir · explicar
CAPA 02 Model Síncrono

Rol: convertir la representación de la señal en una predicción calibrada, consciente de su incertidumbre, y — opcionalmente — especializada para el dominio.

Responsabilidades

  • Clasificación — asignar la señal a una de N categorías.
  • Calibración — las probabilidades deben ser interpretables como frecuencias reales. Un 0.9 debe significar que 9 de cada 10 veces con esa confianza, el modelo acierta.
  • Cuantificación de incertidumbre — distinguir entre "no sé" (epistémica) y "esto es ambiguo" (aleatoria).
  • Versionado del modelo — cada predicción trazable a la versión exacta que la produjo.
  • Especialización — el modelo base general puede fine-tunearse con datos del dominio. No es obligatorio. Es una optimización cuando el modelo general alcanza su techo de calidad, coste o latencia.
Lo que esta capa NO hace: explicar · decidir · aprender online
CAPA 03 Explanation Síncrono

Rol: traducir la predicción en una explicación grounded en documentación del dominio, en lenguaje natural.

Responsabilidades

  • Detección de dominio — ¿la consulta pertenece a este sistema o es ruido?
  • Retrieval — recuperar los fragmentos relevantes a esta predicción concreta.
  • Filtrado de relevancia — descartar fragmentos poco relevantes antes de generar la respuesta.
  • Síntesis — generar una explicación que cite explícitamente las fuentes.
  • Verificación de grounding — comprobar que la respuesta no inventa información.
  • Abstención — si no hay documentación suficiente, decirlo explícitamente en lugar de generar.
Lo que esta capa NO hace: decidir · alertar · modificar la predicción
CAPA 04 Decision Síncrono + Agente

Rol: convertir la predicción y su explicación en una acción concreta y en el nivel de urgencia correcto.

Responsabilidades

  • Routing — decidir qué camino debe tomar cada evento (respuesta inmediata, revisión, log silencioso).
  • Thresholds de acción — cuándo una predicción genera alerta, revisión humana o log.
  • Deduplicación — múltiples eventos del mismo origen en una ventana = una sola alerta.
  • Escalado — niveles de urgencia con canales distintos.
  • Abstención explícita — cuando el modelo declara alta incertidumbre, el sistema no alerta, pero registra para revisión.
  • Orquestación de agente — para casos que requieren múltiples pasos, la capa 4 puede implementar un grafo de estados con checkpointing persistente, interrupción para human-in-the-loop, y trazabilidad de cada nodo.
  • Reconciliación de proveedores — cuando hay múltiples LLM (local + cloud + fine-tuned), la capa 4 decide cuál usar según coste, latencia y criticidad.
Lo que esta capa NO hace: generar explicaciones · modificar predicciones · aprender
CAPA 05 Governance Background

Rol: vigilar que el sistema sigue funcionando en producción, cerrar el loop con el mundo real, y dejar evidencia auditable.

Responsabilidades

  • Drift de datos — detectar cuándo las señales de entrada se parecen cada vez menos a las de entrenamiento.
  • Drift de concepto — detectar cuándo la relación señal→etiqueta está cambiando.
  • Feedback de campo — capturar las correcciones que los operadores hacen y almacenarlas como nuevas etiquetas.
  • Evaluación de la explicación — medir si las respuestas de la capa 3 siguen siendo útiles, correctas y grounded.
  • Almacenamiento analítico — además del almacenamiento operacional, mantener un almacén columnar para preguntas históricas: coste por usuario/mes, distribución de predicciones por día, evidencia de auditoría.
  • Seguridad auditada — cada intento de injection bloqueado, cada output rechazado, cada acceso a secretos, registrado con usuario, severidad y timestamp.
  • Evaluación de especialización — si se fine-tunea el LLM, comparar métricas entre modelo base y fine-tuned antes de promover.
  • Versionado end-to-end — vincular datos + modelo + prompt + configuración en cada iteración.
  • Gates de promoción + rollback automático.
Lo que esta capa NO hace: bloquear el path síncrono · decidir por sí sola
TRANSV. Security Input + Output

Rol: proteger el sistema contra inputs maliciosos y outputs peligrosos.

Responsabilidades

  • Validación de entrada — detección heurística de patrones conocidos, clasificación con modelo pequeño para casos sospechosos, logging de cada bloqueo.
  • Validación de salida — validación estructural con schema estricto para endpoints que devuelven datos estructurados.
  • Guardrails declarativos — flujos predefinidos que el modelo no puede violar (no revelar el system prompt, no hablar de temas fuera de dominio).
  • Auditoría — cada evento de seguridad registrado con la misma trazabilidad que una predicción.
Lo que esta capa NO hace: routing · generar explicaciones · sustituir al LLM
05
Dinámica
Flujo end-to-end · path síncrono vs path de gobierno

Path síncrono — una señal, una respuesta

flujo end-to-endpseudocódigo
1. Sensor emite señal
2. Ingestion: pre-procesa en edge → evento {source_id, features, timestamp}
3. Security: input validation → bloquear o pasar
4. Model: clasifica → {label, confidence, uncertainty}
5. Decision: evalúa thresholds
      ├─ alta confianza + alta urgencia   → alerta inmediata + Explanation
      ├─ confianza media                  → Explanation + revisión
      ├─ baja confianza o alta incert.    → log + revisión silenciosa
      └─ caso multi-paso                  → Agent graph
                                              (clasificar → diagnosticar
                                               → human gate → workorder)
6. Explanation: retrieval + síntesis + verificación
7. Security: output validation → schema, PII, secrets
8. Operador recibe: {label, confidence, explicación, fuentes, acción}

SLA típico: milisegundos (ingesta) + milisegundos (modelo) + segundos (explicación) = respuesta completa en <5s en el percentil 95.

Path de gobierno — background, no bloquea

gobierno continuopseudocódigo
1. Cada predicción se loguea con trace_id
2. Governance muestrea (ej: 20%) para evaluación profunda
3. Operadores confirman/corrigen predicciones → feedback almacenado
4. Periódicamente (diario/semanal):
      ├─ comparar distribuciones → drift score
      ├─ evaluar calidad RAG → faithfulness, precision, recall
      ├─ si hay modelo fine-tuned → comparar base vs fine-tuned
      └─ si algún gate falla → reentrenamiento o rollback
5. Auditoría continua:
      └─ queries analíticas: coste, acceso a secretos, drift

SLA típico: minutos a días. El sistema nunca espera a la capa 5 para responder.

El path síncrono tiene SLA de segundos. El path de gobierno opera en horas o días. Confundir ambos es el error estructural más común.

07
Trade-offs
Lo que ganas · lo que pagas

Lo que ganas

  • Trazabilidad end-to-end — cualquier decisión reconstruible desde el sensor físico hasta la explicación.
  • Fallo silencioso imposible — el drift detection convierte el fallo lento en una alerta explícita.
  • Operador asistido, no reemplazado — el sistema propone, el humano decide.
  • Reutilizable — las cinco capas se reaplican a cualquier dominio que cumpla el contexto.
  • Cumplimiento auditable — soberanía de datos + evidencia de seguridad + versionado de modelos.

Lo que pagas

  • Complejidad operacional alta — son cinco sistemas, no uno. Cada capa tiene su propio ciclo de vida.
  • Latencia acumulada — el path síncrono incluye un LLM. No es un sistema de control reactivo (<10ms). Es un sistema de asistencia.
  • Coste del LLM en el path crítico — la capa 3 cuesta dinero por cada explicación generada.
  • Necesitas datos etiquetados — sin feedback loop real, el sistema no mejora.
  • Requiere disciplina de equipo — cinco capas con responsabilidades claras fallan si un equipo las mezcla.
  • Coste de formación — operar Kafka, LangGraph, Evidently, Langfuse y ClickHouse requiere seniority real.

09
Patrones relacionados
Cómo se combinan con otros patrones conocidos
  • Event Sourcing — la capa 1 puede implementarse como log de eventos inmutable, permitiendo replay.
  • Circuit Breaker — necesario en la capa 3 para tolerar caída de proveedores LLM.
  • CQRS — natural en la separación path síncrono vs path de gobierno.
  • Sidecar / Ambassador — útil para el Request Classifier de la capa 4.
  • Golden Dataset / Evaluation Set — prerequisito para la capa 5.
  • Human-in-the-loop — la capa 4 y 5 lo requieren explícitamente.
  • Backpressure — obligatorio en la capa 1 si los sensores superan la capacidad de cómputo.
  • Saga Pattern — aplicable en la orquestación de agentes cuando hay compensación entre pasos.
  • Feature Store — aparece cuando >3 modelos comparten features.
10
Criterios de éxito
Cómo saber si el patrón está correctamente implementado

Un sistema que implementa SSEP correctamente cumple estas trece condiciones:

  1. Puedo responder "¿por qué el sistema dijo esto?" para cualquier predicción de los últimos 90 días.
  2. El drift de datos se detecta antes de que un operador humano note el fallo en producción.
  3. Cada versión desplegada tiene un gate de promoción con métricas explícitas, no "lo probamos y va bien".
  4. Un falso positivo cuesta menos de 30 segundos de atención del operador (explicación clara + acción sugerida).
  5. El feedback de campo se incorpora al siguiente ciclo de entrenamiento sin intervención manual de ingeniería.
  6. Si el proveedor LLM cae, el sistema sigue prediciendo (solo se degrada la explicación).
  7. La capa de explicación puede abstenerse y decir "no tengo información suficiente" sin inventar.
  8. Cada request al LLM tiene un trace completo (input, output, tokens, coste, latencia, cache hit, proveedor) consultable por usuario y sesión.
  9. La calidad del RAG se mide en producción (faithfulness, precision, recall) y sus scores se vinculan a los traces.
  10. Los intentos de prompt injection se bloquean antes de llegar al LLM y se registran como eventos auditables.
  11. Las respuestas estructuradas no pasan al cliente si no validan el schema — fallo controlado en lugar de salida malformada.
  12. Las preguntas históricas de coste, drift y compliance se responden en <1s sobre millones de filas.
  13. Si se fine-tunea el LLM, hay una comparación explícita base vs fine-tuned con las mismas métricas antes de promover.
✓ Regla de oro Si no puedes responder las trece preguntas con evidencia, no has implementado el patrón — has implementado una parte. El patrón completo incluye las cinco capas, la transversal de seguridad, y el gobierno continuo.
