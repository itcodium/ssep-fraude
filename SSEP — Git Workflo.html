Estructura de ramas
Una rama por peldaño · main siempre estable

Cada peldaño nace de main, vive en su propia rama y vuelve a main cuando el gate está superado. Sin excepciones, sin develop.

main ────●─────●─────────●─────────●─────────●─────────●──► \ / / / / / p1 ───────●───● p2 ─────────────●───●───● p3 ───────────────────────●───● p4 ─────────────────────────────●───● p5 ───────────────────────────────────●───● v0.2 v0.3 v0.4 v0.5 v0.6 v1.0

Reglas

ReglaDetalle
Una rama por peldañoNunca trabajes dos peldaños en la misma rama
main siempre estableSolo recibe merges de gates cerrados (o parciales, con tag explícito)
No hay developCada rama nace de main y vuelve a main
Ramas cortasVida útil = un peldaño. Al mergear, se borra

Naming

PatrónUso
pN-<slug>Ramas de peldaño: p1-modelo-real, p3-llm-real
feature/pN-<slug>Variante para peldaños con varias sub-fases: feature/p2-rag-real
hotfix/<slug>Solo para corregir algo ya en main

Convención de commits
Imperativo · tipo: descripción · máx 72 chars

Formato

<tipo>: <descripción corta en imperativo>

[cuerpo opcional: por qué, no qué]

Tipos permitidos

FEAT
feat: capa1 ingestion con extractor de features
Añade funcionalidad nueva
FIX
fix: clasificador devuelve label vacío con input malformado
Corrige un bug
REF
refactor: separa loader de classify en model.py
Reorganiza sin cambiar comportamiento
DOCS
docs: contratos A2 completados
Solo documentación
TEST
test: 3 casos de abstención en capa3
Añade o modifica tests
CHORE
chore: .gitignore excluye creditcard.csv y __pycache__
Configuración, dependencias, infraestructura
MERGE
Merge branch 'p3-llm-real' - P3 LLM real
Lo genera git con --no-ff, no se escribe a mano

Reglas de estilo

  • Imperativo, no pasado: añade capa2, no añadida capa2
  • Minúscula inicial, sin punto final
  • Máximo 72 caracteres en la primera línea
  • Sin acentos raros en el asunto (portabilidad CLI)
  • Cuerpo opcional separado por línea en blanco: explica el por qué

Ejemplos

EstadoCommit
✓feat: capa1 ingestion con extractor de features
✓fix: clasificador devuelve label vacío con input malformado
✓chore: .gitignore excluye creditcard.csv y __pycache__
✕Añadida la capa 2. — pasado + punto
✕FEAT: Capa 2. — mayúsculas + punto
✕cambios varios — no dice qué
✕wip — no es un commit, es un guardado
3
Versionado (tags)
SemVer simplificado con sufijo de peldaño

Formato

v<major>.<minor>[-<estado>]

Mapa de tags

TagSignificado
v0.2Fases A+B+C cerradas (base validada) — ✅ hecho
v0.3P1 cerrado (modelo real)
v0.4P2 cerrado (RAG real)
v0.4-p2-parcialP2 mergeado pero con tareas pendientes del gate
v0.5P3 cerrado (LLM real)
v0.6P4 cerrado (observabilidad)
v1.0P5 cerrado (evaluación con baseline)
Regla crítica No se tagea un gate parcial con el número limpio. O cierras todas las tareas del gate, o el tag lleva el sufijo -parcial. Tagear como cerrado algo que no lo está rompe la trazabilidad del proyecto.

Comando de tag anotado

git tag -a v0.3 -m "v0.3: P1 cerrado - modelo XGBoost ULB integrado"
  • Siempre -a (anotado, no ligero)
  • Siempre -m con mensaje descriptivo
  • Nunca tag en un commit sin mergear a main
4
Flujo completo de un peldaño
Aplicable a P1, P2, P3, P4, P5 · ejemplo con P3

4.1 Abrir la rama

git checkout main
git pull origin main
git checkout -b p3-llm-real
git push -u origin p3-llm-real

4.2 Trabajar y commitear

Commits pequeños y frecuentes. Cada commit debe dejar el repo ejecutable, aunque sea parcial.

git add .
git status                     # verificar qué entra
git commit -m "feat: cliente Ollama para LLM local"

git add .
git commit -m "feat: prompt grounded con inyección de chunks"

git add .
git commit -m "feat: integración LLM en capa3 explanation"

git push                       # subir progreso, no esperes al final

4.3 Verificar el gate

PeldañoGateVerificación
P1main.py + test_model.py con ULB realejecutar los 3 casos
P2top-5 chunks relevantes, score > 0.25query de prueba manual
P3faithfulness > 0.7 en 10 queriesevaluación manual
P4100% de requests con trace completoabrir Langfuse
P5faithfulness > 0.8 en baselineRAGAS
Si el gate no está cerrado No mergees como vX.Y limpio. Usa el sufijo -parcial en el tag y documenta qué falta en el mensaje.

4.4 Mergear a main

git checkout main
git pull origin main

# Ver qué va a entrar (siempre, antes de fusionar)
git log --oneline main..p3-llm-real
git diff --stat main..p3-llm-real

# Fusionar preservando la topología
git merge --no-ff p3-llm-real -m "Merge branch 'p3-llm-real' - P3 LLM real"
¿Por qué --no-ff? Fuerza un commit de merge explícito. Sin él, si la rama era lineal, git haría fast-forward y perderías el rastro de que existió una rama. Con --no-ff el git log --graph muestra claramente cada peldaño como una unidad.

4.5 Tagear el hito

# Gate cerrado
git tag -a v0.5 -m "v0.5: P3 cerrado - LLM grounded integrado"

# Gate parcial
git tag -a v0.5-p3-parcial -m "v0.5-p3-parcial: LLM integrado. Pendiente P3.2 (prompt grounded)"

4.6 Publicar y limpiar

git push origin main
git push origin --tags

# Borrar la rama ya fusionada (local y remoto)
git branch -d p3-llm-real
git push origin --delete p3-llm-real

4.7 Verificación final

git branch
# → * main

git log --oneline --graph -10
# → *   <sha> Merge branch 'p3-llm-real' - P3 LLM real
# → |\
# → | * <sha> feat: integración LLM en capa3 explanation
# → | * <sha> feat: prompt grounded con inyección de chunks
# → | * <sha> feat: cliente Ollama para LLM local
# → |/
# → * <sha> (tag: v0.4) Merge branch 'feature/p2-rag-real'

git tag -l
# → v0.2
# → v0.4
# → v0.5

git status
# → On branch main
# → Your branch is up to date with 'origin/main'.
# → nothing to commit, working tree clean

Checklist rápida
Imprimir y tener al lado

Antes de commitear

  • git status no muestra basura (__pycache__, CSV, .env)
  • El mensaje sigue la convención <tipo>: <descripción>
  • El commit deja el repo ejecutable

Antes de mergear

  • El gate del peldaño está cerrado (o decidido como parcial)
  • git log main..<rama> muestra los commits esperados
  • git diff --stat main..<rama> no incluye archivos inesperados
  • main está actualizado (git pull origin main)

Después de mergear

  • git log --oneline --graph muestra el merge con --no-ff
  • Tag creado con -a y mensaje descriptivo
  • git push origin main && git push origin --tags
  • Rama borrada (local y remoto)
  • git status → "working tree clean"
  • GitHub muestra el tag en /tags y el merge en /commits/main

Troubleshooting
Los 6 problemas más frecuentes
"Your branch and 'origin/main' have diverged"
git pull --rebase origin main
# Resolver conflictos, luego:
git rebase --continue
Merge conflict en X
# Abrir el archivo, resolver, luego:
git add X
git merge --continue
# O cancelar:
git merge --abort
Olvidé el tag y ya pusheé
# Crear tag en el commit correcto (por SHA)
git tag -a v0.3 -m "..." <sha-del-merge>
git push origin v0.3
Quiero deshacer el último commit (sin pushear)
git reset --soft HEAD~1     # deshace commit, mantiene cambios en staging
git reset --mixed HEAD~1    # deshace commit, cambios sin stagear
Quiero deshacer un tag
git tag -d v0.3                    # local
git push origin --delete v0.3      # remoto
Olvidé crear la rama y trabajé en main
# Mover los commits a una rama nueva
git branch p3-llm-real
git reset --hard origin/main
git checkout p3-llm-real

System prompt
Versión ejecutable · para LLM o agente

El resto de esta página es para humanos. Esta sección es para que un LLM opere el repo: valide commits, bloquee anti-patrones y ejecute el flujo de merge en orden. No reemplaza al HTML — lo ejecuta.

Cómo se usa Pega el bloque completo como system prompt al iniciar una conversación, o guárdalo como GIT-WORKFLOW.prompt.md en el repo para cargarlo como contexto. Si cambias una regla aquí, actualiza también las secciones 1–10: son la misma verdad, en dos formatos.

Tres formas de consumirlo

Opción A
System prompt
Pégalo al inicio de una sesión con Claude, GPT o DeepSeek. El modelo adopta el rol de guardián del workflow.
Opción B
Archivo del repo
Guárdalo como GIT-WORKFLOW.prompt.md junto a este HTML. Sirve como contexto versionado.
Opción C
CLAUDE.md / AGENTS.md
Si usas Claude Code o un agente similar, este contenido va ahí y el agente lo aplica en cada sesión.

Prompt

SSEP · git-guardian · v1 
Eres el guardián del git workflow del proyecto SSEP.
Tu trabajo: validar y guiar commits, ramas, tags y merges.
Nunca ejecutas comandos; propones y verificas.

## Invariantes (no negociables)

1. Una rama por peldaño. Nace de main, vuelve a main.
2. main siempre estable. Solo recibe merges de gates cerrados.
3. Un gate superado = rama mergeada con --no-ff + tag anotado + push.
4. Si el gate está parcial, el tag lleva sufijo -parcial. Nunca tag limpio.
5. Nunca se versionan datasets (creditcard.csv, archive.zip) ni .env.

## Formato de commit

<tipo>: <descripción imperativa, minúscula, sin punto, ≤72 chars>
Tipos: feat | fix | refactor | docs | test | chore
Cuerpo opcional separado por línea en blanco (explica el por qué).

## Formato de tag

v<major>.<minor>[-<estado>]
- vX.Y solo si TODAS las tareas del gate están cerradas.
- vX.Y-<peldaño>-parcial si falta alguna. El mensaje debe listar qué falta.

## Flujo de merge (orden obligatorio)

1. git checkout main && git pull origin main
2. git log --oneline main..<rama>          ← mostrar al usuario
3. git diff --stat main..<rama>            ← mostrar al usuario
4. git merge --no-ff <rama> -m "Merge branch '<rama>' - <peldaño>"
5. git tag -a <tag> -m "<mensaje>"
6. git push origin main && git push origin --tags
7. git branch -d <rama> && git push origin --delete <rama>
8. git status                              ← debe decir "working tree clean"

## Rechaza y explica si el usuario pide

- git push --force a main                    → reescribe historia compartida
- git merge sin --no-ff                     → pierde topología
- tag vX.Y con gate parcial                 → rompe trazabilidad
- git add -A sin revisar git status         → mete basura
- tag sin mergear a main                    → tag huérfano
- trabajar directo en main                  → sin rama no hay gate
- commit -am "wip" o "cambios varios"       → no describe nada
- git add -f sobre CSV/zip/.env             → dataset en el repo

## Cómo respondes

- Si el usuario pide un commit: valida el mensaje contra el formato,
  propón corrección si falla, no inventes commits.
- Si pide merge: ejecuta el flujo de 8 pasos en orden, marcando qué
  verificar en cada uno.
- Si pide tag: pregunta primero "¿está cerrado el gate o es parcial?"
  y aplica la regla.
- Si pide algo de la lista de rechazo: bloquea, explica por qué,
  ofrece la alternativa correcta.
- Si pide troubleshooting: das el comando, no la teoría.
